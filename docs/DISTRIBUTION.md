# Distribution and pricing

## Recommended launch path

Keep the source repository public and use **GitHub Releases as the canonical download source** for the first launch. A small marketing website can come later; its Download button should point to the latest GitHub Release rather than hosting a second copy of the binary.

This gives PitchKiwi one source of truth for code, issues, release notes, binaries, and checksums. It also lets technical users audit and build the app while nontechnical users download one ZIP.

## What users download

Each release should contain:

- `PitchKiwi-macOS.zip` — the complete application bundle, including the default local Whisper model;
- `PitchKiwi-macOS.zip.sha256` — the checksum generated by `make release`;
- concise release notes with the supported macOS and hardware versions;
- a link to the source commit used to build it.

The user downloads the ZIP, moves `PitchKiwi.app` to Applications, and opens it. Do not ask users to download the source repository or run build commands unless they deliberately choose the developer path.

## Website versus GitHub

Use both for different jobs:

| Surface | Job |
| --- | --- |
| Simple website | Explain the product in seconds and send visitors to Download |
| GitHub repository | Source, trust, documentation, issues, and development |
| GitHub Releases | Canonical app download, release notes, and checksums |

A website is optional at launch. It does not need accounts, a database, or a backend. Static hosting on GitHub Pages, Cloudflare Pages, or a similar service is enough.

## Free or paid

For the current public MIT repository, launch **free** and optionally accept sponsorships or tips. This is the clearest fit for a project built quickly, with no ongoing service cost, and it avoids introducing license validation or customer-support obligations before the app is proven.

A `$5 lifetime` download is possible, but the tradeoffs must be explicit:

- an MIT-licensed public repository cannot meaningfully prevent people from building and sharing the app for free;
- a license gate adds a network call and makes the privacy story more complicated;
- payment creates expectations around support, updates, refunds, signing, and compatibility;
- selling a convenient signed/notarized build while keeping the source free is possible, but payment should not be marketed as required if users can legally build it themselves.

Do not add Gumroad licensing or make the repository private until the business model is deliberately chosen. Changing license terms cannot retroactively revoke rights already granted to copies released under MIT.

## Safety checklist before a broad public download

1. Enroll in the Apple Developer Program.
2. Sign the app with Developer ID and enable the hardened runtime.
3. Notarize and staple the distributed app.
4. Publish the SHA-256 checksum for every release.
5. Enable GitHub two-factor authentication and protect the `main` branch.
6. Enable GitHub Private Vulnerability Reporting.
7. Keep signing certificates, tokens, transcripts, recordings, and local settings out of Git.
8. Build releases from a clean tagged commit and retain the exact build log.

Making the repository public does not expose a user's microphone, transcripts, or local PitchKiwi data. Those files live outside the repository and are ignored by Git. The meaningful risks are compromised maintainer credentials, leaked signing keys, malicious dependencies, or unreviewed release changes, so the release process and account security matter more than hiding ordinary source code.
